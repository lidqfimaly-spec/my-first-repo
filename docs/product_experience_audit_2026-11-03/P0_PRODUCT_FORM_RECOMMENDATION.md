## 选项分析

### A. Web 优先（远程）

**[事实]** registry：`deployment_scope=single_host_local_alpha`；`web_ui` limitations 写明无远程/多用户/认证；workbench 拒绝非 loopback。  
**[推断]** 立刻做公网 Web 会强迫补认证、租户隔离、远程代码执行面——与当前 L1 assurance 和 fail-closed 模型冲突。  
**[建议]** 暂缓远程 Web。

### B. Desktop 优先（Electron/Tauri 等）

**[推断]** 利于「像 Manus Studio / Claude Desktop」感知；但现有 vanilla workbench + CLI 已覆盖本地操作员场景；上桌面前需包装安装器、自动更新、OS 权限——成本高。  
**[建议]** 作为中期选项，不作为本阶段迁移目标。

### C. Web + Desktop

**[推断]** 双端同步状态与发布管线成本最高；在双工具 Alpha 阶段过早。  
**[建议]** 不建议本阶段。

### D. 本地优先：CLI + loopback 简中工作台/控制中心（推荐）

**[事实]** 代码与 DESIGN 已采用该形态；控制中心 v1 已交付（git `65981ef`）。  
**[事实]** 安全默认：loopback、Origin+process token、只读 API 与控制动作分离。  
**[推断]** 最匹配「可验证本地执行内核」定位；产品体验债在**引导与控制中心闭环**，不在换壳。  
**[建议]** **推荐保持并打磨该形态**：默认入口改为「控制中心（可写）」，只读台作为审计视图；CLI 保留为权力用户与脚本面。

## 推荐结论

**[建议] 短期（下一阶段）**：坚持 **本地优先 — CLI + loopback 控制中心/工作台**；禁止擅自迁移到远程多租户 Web 或重桌面壳。  
**[建议] 中期验证点**：若用户强需求「关终端仍看任务」，再评估轻量 Desktop 包装（仍绑本机 runtime），或受控局域网认证——须单独立项与威胁模型。  
**[建议] 成功标准**：非工程师用户能在控制中心完成「创建→确认→看事件→取产物」而无需记忆 task_id；能力边界始终可见。

## 明确不做（本阶段）

- 不实施技术迁移  
- 不引入前端重框架仅为「像竞品」  
- 不把云端多 agent 编排形态塞进本仓 Alpha
