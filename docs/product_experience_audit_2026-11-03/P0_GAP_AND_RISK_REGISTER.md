## P0

### P0-1 产品承诺「通用多步 Agent」与运行时「单步双工具」落差

1. **问题**：用户自然语言多目标无法真实执行；系统压成单操作或澄清。  
2. **证据**：场景2实测 `awaiting_clarification`；`policy.py` 单步；registry 仅两操作。  
3. **影响**：核心目标「理解-规划-多工具执行」在 Alpha 不可交付；信任透支。  
4. **根因**：有意收窄执行面 + 对外愿景未同步降级。  
5. **建议**：产品文案/UI 以 registry 为准；另立「多步路线图」隔离承诺。  
6. **备选**：做「向导式伪多步」（人工串多个单步任务）而不开放通用 shell。  
7. **依赖**：产品叙事决策先于扩工具。

### P0-2 「不会用」——成功路径对结构化参数/入口分裂敏感

1. **问题**：只读 workbench 不能提交；CLI 参数多；conversation 强制 client-message-id。  
2. **证据**：workbench POST 405；control-center 才是写入口；场景1需完整 flags。  
3. **影响**：新用户打不开价值闭环。  
4. **根因**：先内核后体验；控制中心仍可选心智。  
5. **建议**：默认启动控制中心 + 首跑向导；常驻能力边界。  
6. **备选**：提供 `zevorinth quickstart` 交互问答。  
7. **依赖**：不改内核契约即可做 UX。

## P1

### P1-1 阶段号漂移（doctor 3.75 vs registry/README 3.92）

1. **问题**：操作员与自动化读到冲突阶段。  
2. **证据**：`cli.doctor_report` 硬编码 `"phase": "3.75"`；`capabilities.product_stage="3.92"`。  
3. **影响**：验收与对外沟通混乱；像未发布完。  
4. **根因**：阶段推进未同步 doctor 字符串。  
5. **建议**：doctor 只读 registry.product_stage。  
6. **备选**：双字段显式 `legacy_phase`（已有类似字段）并弃用主 phase 硬编码。  
7. **依赖**：小改动；需测试更新。

### P1-2 执行中改向/追加与暂停缺失

1. **问题**：无 pause；revise 拒绝执行后任务；长任务干预点不足。  
2. **证据**：无 pause 命令；`revise_plan` 冲突条件；control actions 不含 running cancel/recovery。  
3. **影响**：复杂任务用户失控感；场景3/5失败。  
4. **根因**：任务极短假设 + 安全保守。  
5. **建议**：先产品化 `request-cancel` 与状态说明；pause 暂缓。  
6. **备选**：仅支持「取消后带草稿重建」。  
7. **依赖**：若引入长跑 run_tests/多步则升级为 P0。

### P1-3 Agent 能力与界面脱节（对话助手叙事弱）

1. **问题**：conversation history 缺助手解释；UI 不教用户下一步。  
2. **证据**：process 后 history 仅用户消息；DESIGN 避免聊天气泡但未替代「系统说明」。  
3. **影响**：多轮上下文「不合理」体感。  
4. **根因**：会话层服务任务绑定而非辅导。  
5. **建议**：写入结构化 system/outcome 消息（非娱乐聊天气泡）。  
6. **备选**：仅在控制中心状态条提示下一步动作。  
7. **依赖**：conversation schema 扩展。

### P1-4 部分成功/多交付模型缺失

1. **问题**：无法表达部分失败。  
2. **证据**：单步策略；场景7。  
3. **影响**：真实复杂工作不可建模。  
4. **根因**：有意范围。  
5. **建议**：短期用「任务图/人工串联」文档化；中期再开多步。  
6. **备选**：conversation 多 task 列表视图。  
7. **依赖**：多步设计。
