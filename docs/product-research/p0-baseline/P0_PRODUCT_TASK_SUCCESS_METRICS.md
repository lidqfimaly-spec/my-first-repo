## 1. M-02 端到端成功率（唯一现在就能算的硬指标）

```sql
-- 口径：提交即分母；分子要求三重成立
分子: task.status='succeeded'
      AND verification.passed = 1
      AND artifact 存在且 observed_sha256 = registered.sha256
分母: 该时间窗内 status 不为 'cancelled' 的任务数（cancelled 单独统计，不进分母）
```

**为什么这一条可信**：`SUCCEEDED` 只能从 `VERIFYING` 进入（`state_machine.py:24-108`），
而 `VERIFYING` 的出口由 `verifier.verify` 决定（`service.py:6958-6969`）。也就是说，
**这个指标的分母不被产品话术污染，分子由独立回读决定**。

**它的局限**：只覆盖 7/8 个工具（`controlled_shell` 验证弱，见 R-09）；不含"用户是否满意"。

## 2. M-08 错误成功率（必须重点控制的负向指标）

### 2.1 结构上已经挡住的部分

| 挡法 | 机制 |
| --- | --- |
| 工具说成功 ≠ 任务成功 | `SUCCEEDED` 只能从 `VERIFYING` 进 |
| 文件写了但内容不对 | `artifact_content_mismatch`（重读比对字节） |
| 证据被伪造 | `tool_evidence_mismatch`（逐字段核对回读结果） |
| 事后被改 | `artifact_observation.matches_registration` |

### 2.2 仍然漏掉的三种

| 漏法 | 例子 | 证据 |
| --- | --- | --- |
| `controlled_shell` 只看形状 | 在空目录跑 `ls`，输出 `""` 仍 `passed=true` | `service.py:6166-6175` |
| `run_tests` 只信 evidence 的 `exit_code` | 验的是证据自洽，不是"测试真的通过" | `verifier.py:340-358` |
| 语义正确性 | 写了一个格式合法但内容错的文件（如把"加法"写成"减法"）→ 验证通过 | 验证是字节级，不是语义级 |

### 2.3 怎么才能真正测出来

需要**用户侧判定**：任务结束后问一句"这个结果对吗？"，或在"下载/继续"动作里隐含确认。
没有这个信号，M-08 只能靠人工抽样。

`RECOMMENDATION`：V1 加一个极轻的确认点（结果卡片上的"✓ 可用 / ✗ 不对"），
把 M-01 与 M-08 一起解锁。成本 S，价值极高——它是唯一能发现"语义级错误成功"的通道。

## 3. M-07 人工干预成本（最能反映产品体验的指标）

```
M-07 = (用户消息数 + 表单提交数 + 控制动作数) / 完成任务数
```

现有数据即可计算：
- 消息数：`conversation_messages` 按 `role='user'` 计数；
- 表单/动作：`control_action_*` 事件计数。

**基线样例（本轮实测）**：
- 写文件（对话路径）：4 条消息 + 0 动作 = **4.0 次干预 / 1 个任务**；
- 写文件（表单路径）：1 次 preview + 1 次创建 + 1 次启动 + 1 次下载（尚不存在）= 约 3 次；
- 改代码：1 次创建 + 1 次启动 = 2 次，但要求用户自己算 `expected_sha256`。

`INFERENCE`：M-07 > 3 的任务，用户会认为"还不如自己干"。这是最直接的产品红线。

## 4. 采样与统计纪律（沿用 P0-2 的经验）

1. 分母为 0 → 记 `N/A`，**不记 0%**。
2. 单次运行 = 一个样本，不得外推稳定性。
3. 必须保留失败样本（不许只报成功）。
4. 口径变更必须留痕，不得为提升数字调整口径。
5. 每个指标声明适用范围（模型/机器/任务类型）。
6. 每个指标声明"谁是 ground truth"——没有 ground truth 的指标必须标 `NOT_MEASURABLE`。
