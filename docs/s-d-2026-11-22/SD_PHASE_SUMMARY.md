> 先保证批准的内容就是实际执行的内容，再保证失败后能够安全地继续；

- 「失败后安全继续」：**机制成立，产品不成立**。服务层能安全续跑，但没有任何界面入口；
  且一旦接入界面，会绕开控制面的启动门禁——所以必须先解决 §3 的 P0。
- 「有资格讨论开放入口」：**目前没有资格**。理由见 `F09_PERMISSION_ASSESSMENT.md` §1.3：
  `execute_plan` 今天就已经能被启动（pause → resume），门禁是装饰性的。在门禁真正生效之前

| `src/zevorinth/approval_preview.py` | 适配摘要新签名 | 适配 |

### 2.2 找到并修掉四个真实缺陷

1. **执行期门禁用的是循环局部副本 `task`**（而不是每轮重读的 `latest`）——
   同一循环内批准被撤销时存在沿用旧副本的窗口。**已修，但没有测试能单独证明它**（R-26）。
2. **`TaskNotFound` 在两处 `except` 中被引用却从未导入** —— 异常真抛出时变成 `NameError`，
   把"任务不存在"伪装成"代码崩了"。写探针时现场撞到。**已修。**
3. **续跑只入队不执行** —— 而 `execute_plan` 不可由控制面启动，续跑任务会永远卡在 `QUEUED`。
   **已修**（`return self.execute_task(...)`，与 `submit_plan` 一致）。
4. **副作用判定过度拒绝** —— `child_task_id is None` 被归为"可能已产生副作用"，
   而它其实属于"尚未开始"。**已修**，改为凭 `step_started` 事件里宣布过的 id 查库判断；
   可见变化是拒绝理由从误导的 `step_side_effect_uncertain` 变成真实原因
   （`step_output_field_missing`）。**结论不变，变的是理由**，不夸大。

### 2.3 一个没有修的洞（本阶段最重要的发现）

**`execute_plan` 今天就可以被启动**：`pause_task` → `resume_task`。
控制面实测，两个文件真实落盘，而 `CONTROL_STARTABLE_OPERATIONS` 自始至终不含它。

同一个旁路打 `run_tests` 打不动（`isolation_unverified`），因为后者后面还有隔离证据和
一次性 host grant 两道锁。**这就是两个 F-09 决定必须分开的实证依据。**

没有修，因为修它要改控制面的权限判定条件（等于改 operation 白名单的实际效力），
属于指令保留事项。方案见 `F09_PERMISSION_ASSESSMENT.md` §5.1 P0。

## 4. 需要决策的三件事（按顺序）

### P0　关掉 `execute_plan` 的启动旁路

`pause_task` → `resume_task` 对"从未启动过的任务"在语义上就是 start，不应有两套门槛。
给 `resume_task` 加一条：`PAUSED` 且 `claim_generation == 0` 且
`execution_mode is NOT_EXECUTED` 时，`request.operation` 必须 ∈ `CONTROL_STARTABLE_OPERATIONS`。

**这个改动与 F-09 是否开放无关**：它只是让"不开放"这句话变成真的。
连带影响需要复跑 `test_workbench_control.py` 全部 pause/resume 组合。

### P1　续跑接入控制面

需要新增一个 action（如 `continue_failed_plan`）。**建议排在 P0 之后**——
否则只是又开了一个能启动多步任务的入口。

### P2　F-09 本身

`execute_plan`：P0 + P1 + 「多步里是否允许 `run_tests` 步骤」+ 计划整体形状校验。
`run_tests`：需要 grant 跟着请求走的**新权限传递协议**，不是加白名单条目。
