## 机制级教训（要记住的）

1. **「评测器身份」不等于「实验身份」**：摘要只钉住 `code_edit_baseline.py` 的 21 个符号，
   而 5/9 指标由 `validate_proposal_candidate` / `apply_text_edit`（别的文件）决定。
   补法：`freeze.dependencies` 记产品组件摘要 + VCS 修订 + provider 报文（`ModelReply.raw`
   目前在 `run_baseline` 被丢弃，所以「实际返回模型」只能追溯到自己的提取逻辑）。
   → 属记录契约变更，要升 `code-edit-evaluator-v3`，本轮按评审决定**不做**。
2. **自指哈希只防误改、不防篡改**：`test_the_evaluator_is_frozen` 断言
   「`evaluator_identity()` 的返回值 == 常量」，而 `evaluator_identity` 无法把自己放进名单（无限递归）。
   兜底实际是 `ScriptedRunTests` 的精确数字，而测试不在身份内。缓解只能靠外部锚点
   （仓库外评审记录 / 提交号绑定）。这个极限要在文档里明说，不能说成「冻结证明评测器可信」。
3. **辅助字段不在摘要内**：`CaseResult.passed` 可把 `per_category` 通过数 11/15 → 15/15；
   `ProbeResult.correct` / `MODEL_*` / `GATE_*` 可改 `failures` 归因。九项指标不动，但报告呈现变。
4. **对照探针守卫是单向的**：删全部 `accept` → fail-closed；**删全部 `reject` 仍能加载**，
   `precision_gate_rejection` 变 `N/A`。「必需指标分母为 0」目前只渲染成 N/A，不算加载错误。
5. **`EVALUATOR_VERSION` 是纯标签**：改 `v9` 而摘要不动，两者无绑定。
6. **G 缺口可被走热**（不再只是理论可达）：`no_change_hint_normal` 上加行内注释的 3 行候选，
   `accepted/modified=True, violations=[]` → 只进两个分母、不进任何分子。
